# Google public signup implementation research

Status: research and proposed implementation only. No Google client configured, product changes deployed, or accounts modified by this research. Preserve Schedule C isolation and finish the three existing users' hosted password-login checks first.

Reviewed against current Google documentation and the hosted-baseline code. Changes from the first draft: explicit atomic challenge storage, account-wide session revocation, callback-specific CSRF handling, React/GIS lifecycle and logout behavior, email collision rules across both email stores, browser support, and the identity-only testing exception. These are implementation requirements; this review did not exercise a real Google client.

## Recommended flow

Use the current Google Identity Services Sign in with Google button with a JavaScript credential callback. The React callback sends the Google ID token to the API over HTTPS using the existing apiFetch helper. Verify it with Google's Node google-auth-library, then establish the app's existing Passport/PostgreSQL session. Google authenticates identity; the application decides signup, linkage, ownership and access.

The popup/callback approach needs a web client ID and authorized JavaScript origins, not an application-side authorization-code exchange or client secret. An authorized redirect URI is needed only if redirect mode is chosen instead. The ID token is not a Google API access token. Request only basic identity; no Drive, Gmail, Calendar, offline access or stored refresh tokens.

New visitors can create accounts with Google without owner invitations. Existing password users retain password access and can connect Google from Settings after completing their temporary-password change and proving current account access. Connecting Google preserves User.id and all business foreign keys. Do not automatically connect by username or matching email. If a new Google signup collides with an existing User.email, ask the user to sign into that existing account and connect Google. Email ownership can change; Google subject is the stable identity key.

Do not apply generic 100-test-user/refresh-token-expiry assumptions to this flow. Additional API scopes change those rules. Still verify the project's audience, branding and actual access using an unrelated Google account before release; Workspace/Advanced Protection restrictions can affect individual users. Configure the owned authorized domain carltechs.com and complete any required domain/brand verification. Basic identity scopes avoid sensitive API-scope review, but do not imply exemption from all branding/policy requirements.
5. Netlify VITE_GOOGLE_CLIENT_ID and Render GOOGLE_CLIENT_ID must match the intended client. Client ID is public; an ID token remains a secret and must not enter logs, URLs or alerts.
6. Load GIS from Google's hosted gsi/client script. Check the production Content Security Policy and popup/FedCM behavior; follow Google's supported headers rather than bypassing browser restrictions.

## Proposed app changes

- Add an additive GoogleIdentity model with unique Google subject and an existing User.id foreign key. Initially permit one linked Google identity per user with a unique user_id. Store identity metadata separately; do not rewrite old Discord emails/IDs or LocalCredential login identifiers.
- Add the account-wide User.login_disabled and User.auth_version policy described below, shared by password and Google sessions. LocalCredential.disabled currently controls password access; Google must not unintentionally restore access that the owner meant to revoke globally.
- Separate provider authentication from business authorization. The current passwordAuth.sessionGuard rejects every non-password session or account without LocalCredential. Extend/refactor it into a shared guard that checks the selected provider's current credential/identity version and account status. Google-only new users do not require LocalCredential. Preserve forced password changes for password sessions and reject old Discord sessions.
- POST /auth/google/challenge: create a short-lived, database-backed and session-bound challenge and nonce; distinguish login from authenticated link intent. POST /auth/google verifies the identity token, atomically consumes that challenge and establishes a login/signup session. POST /auth/google/link requires authenticated account access, recent password reauthentication for the migrated users, and a separate link challenge. Bind account ID to the server session, never a supplied user ID.
- Verify token signature, issuer, audience, expiry, nonce and subject; handle email claims under an explicit collision policy. Enforce exact allowed Origin and CSRF checks on callback JSON requests using apiFetch, alongside nonce/replay controls. For a Google direct-form redirect flow instead, implement Google's g_csrf_token cookie/body validation rather than broadly exempting authentication endpoints from CSRF checks.
- Create User plus GoogleIdentity atomically; initialize only that new user's defaults. Unique constraints and conflict handling must make simultaneous first signups idempotent without duplicate users or orphan records. Link only if the subject is not already attached to another account. Consume challenges once and preserve records on failed linkage.
- Regenerate and explicitly save PostgreSQL sessions before reporting success. Return an explicit public user shape with the correct auth provider. Keep Google tokens out of responses after verification, persistent sessions and browser storage. Provider verification failures must not trigger unbounded retries.
- Add the Google button beside password login and an authenticated Connect Google action in Settings. Public signup is through Google; password creation remains an owner/account-management flow, not an unintended public registration endpoint. Unlink must not leave an account with no usable login; it can be a later focused task if omitted initially.
- Rate-limit challenge/signup/link endpoints and bound outbound verification work. Current attempt limits are process-local: account for deployments/replicas before public release. Keep password login available during Google outages. Google has its own service limits; it cannot guarantee immunity from provider outages or rate limits.

## Requirements tightened during review

### Challenge storage and callback validation

Change challenge creation to POST /auth/google/challenge, with the existing custom request header plus an exact server-side allowed-Origin check. CORS response configuration alone is not an Origin rejection middleware. Use an AuthChallenge database row rather than trusting a value deleted from req.session: concurrent requests can read the same stored session and both proceed. Store a random challenge identifier, nonce, server-session binding, intent, expiry and consumed status; use a short TTL (initially five minutes), bounded outstanding rows and cleanup. Link challenges also bind the authenticated User.id and current account session version.

An anonymous challenge request must explicitly establish and save a session before returning the challenge: saveUninitialized is false today, so merely reading req.sessionID does not persist a session or send its cookie. Treat cookie/session-save failure as a failed challenge issuance and clean up unusable challenge rows. Response caching must be disabled for auth/challenge endpoints. Test cookie continuity through both the configured direct API origin and Netlify proxy.

After library token verification, explicitly compare payload.nonce to the challenge nonce. The library's standard verifyIdToken verification must not be assumed to perform this application-specific comparison. Consume the unexpired, correctly bound challenge using a conditional database update in the same transaction as signup/link changes; exactly one callback wins. No Google network calls inside the transaction. A failed verification does not mutate business/account records. Expiry, retry and concurrent callbacks must have explicit responses and require a fresh challenge when appropriate.

For the chosen JavaScript popup callback, our application constructs its own JSON POST; do not assume Google's direct-form g_csrf_token is automatically added to apiFetch. Protect it with allowed Origin, custom-header enforcement and server-bound nonce/challenge validation. The double-submit g_csrf_token validation in Google's documentation applies when accepting GIS direct-form delivery. Do not add a blanket CSRF bypass. Never accept a client-supplied audience/client ID as the verification allowlist. [Token verification](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token), [Google library source](https://raw.githubusercontent.com/googleapis/google-auth-library-nodejs/main/src/auth/oauth2client.ts)

### Account status, sessions and identity collisions

Make account-wide status concrete: User.login_disabled and User.auth_version, checked fresh from the database on authenticated requests, together with provider identity/credential status. User deserialization currently has a five-minute cache, so cached flags cannot enforce immediate revocation. Existing disabled credentials require an explicit conservative migration policy; Google must not reopen a disabled account. Owner resets/account revocations increment the account session version to invalidate every provider's older sessions. Reissue the active session with the current versions after successful sensitive changes. Provider unlink/replacement is deferred until a safe recovery design exists; do not expose an incomplete unlink button.

For an already-linked subject, use GoogleIdentity.user_id even if Google changes its email; do not create another user or rewrite legacy email. For a first signup, validate the signed email claim and require email_verified under the chosen product policy, but never treat that alone as authority to take over an existing account. Check collisions with both User.email and LocalCredential.email because password identifiers are now stored separately. Resolve collisions through authenticated linking; do not merge by email, strip Gmail dots, or guess aliases. Validate and limit profile fields, ignore any supplied role/permissions, and derive ownership only from server identity. Google subject remains the unique provider key. Race-safe email collision handling must cover any future account email-management operation as well.

Session-save failures after account creation/linking require honest recoverable responses. The user/identity transaction may already have committed; don't claim nothing changed or delete an existing account. A subsequent login finds the same identity rather than creating another account. Separate frontend query caches by User.id or clear them on login/logout/account switches so cached records from the previous user cannot appear to the next user on a shared browser.

Only the narrowly defined Google login/challenge entry routes may recover from an invalid legacy session; link routes must retain full authentication/account checks. Do not broadly bypass the guard for /auth/google/*. Avoid silently switching an already-authenticated account through a login callback; require explicit account-switch intent or logout, and distinguish that from attaching an identity.

### React, browser support and logout

Use one GIS script loader and a centralized configuration lifecycle. google.accounts.id.initialize is global to the page and later calls replace earlier settings; multiple components and React StrictMode must not overwrite each other's callback/nonce. Allow one active intent per document, render the button only after its saved challenge is ready, and refresh configuration deliberately after expiry/retry or changing login/link intent. Keep auto_select and button_auto_select off and defer One Tap. Use Google's rendered button rather than an imitation that might violate branding or popup gesture requirements. Logout destroys the app session and calls disableAutoSelect when GIS is loaded; logout is different from revoking Google's grant. [JavaScript reference](https://developers.google.com/identity/gsi/web/reference/js-reference)

Test in normal Chrome, Edge, Firefox and Safari plus mobile supported browsers. Google explicitly does not support Android/iOS webviews for sign-in. Embedded desktop browsers are not proof of compatibility; Google can reject embedded user agents. Provide guidance to open the site in a supported regular browser, without bypassing provider restrictions. Test popup-blocking, tracking protection, FedCM and installed-PWA behavior. Configure a supported COOP policy for non-FedCM popups and GIS CSP resources only where needed. Don't blanket-disable browser protections. [Supported browsers](https://developers.google.com/identity/gsi/web/guides/supported-browsers), [Embedded-browser guidance](https://developers.googleblog.com/guidance-to-developers-affected-by-our-effort-to-block-less-secure-browsers-and-applications/)

### Public launch and recovery

Google signup is public, but every new User still owns only their own records and receives no administrative permissions. Before public enablement, reproduce or confirm resolution of the existing QA permission findings against the actual hosted branch. Any unresolved tenant-isolation issue is a separate focused fix and a launch blocker, not something to silently bundle into authentication. Set durable signup/challenge attempt limits (PostgreSQL atomic counters or an explicitly configured shared service), trusted-proxy/IP handling, small auth request-size limits and bounded verification timeouts. The current seven-megabyte global body parser and process-local login counter are not sufficient specifications for public signup abuse controls.

Place the small auth body limit before the current global JSON parser; a downstream parser cannot undo a large body already read upstream. Wrap Google verification failures in new fixed safe errors rather than forwarding the raw library exception to logs/Sentry: the reviewed Google library includes token text in some malformed-token error messages. Keep only allowlisted diagnostic categories and a request correlation ID. Reuse a verification client with its supported certificate cache and bounded transport retries; do not create a new client or fetch keys repeatedly for every callback. [Google library source](https://raw.githubusercontent.com/googleapis/google-auth-library-nodejs/main/src/auth/oauth2client.ts)

For Google-only users, document recovery via their Google account; no public local password-reset system is implied. The migrated three retain their existing owner-reset/password path. Feature flags must distinguish stopping new Google signup from stopping returning Google login: a signup kill switch must not accidentally lock out Google-only existing users. Verify cold-start behavior, absent/mismatched client IDs, stale PWA assets and outage fallback. Errors must be scrubbed before Sentry/logging so a rejected request cannot leak the raw credential or challenge.

## Focused QA and release

Test first signup, returning Google login, cancellation/popup blocked, duplicate clicks, expired/wrong-audience/wrong-issuer/invalid-signature tokens, wrong nonce/replayed challenge, missing fields, unexpected supplied owner IDs, both email-store collisions, concurrent signup and simultaneous replay, identity already linked elsewhere, link failure rollback, disabled/revoked users across both providers, post-commit session-save failure, logout/relogin and actual restart persistence. Test cached revocation, multi-tab/StrictMode challenge lifecycle, account switching/query-cache clearing, non-authoritative email claims, changed Google email, a signup-only kill switch and auth limits surviving restart. Exercise public signup with an account outside the initial three. Verify separate inventories/sales/settings across users and regress existing password/temporary-password flows. Review relevant existing QA permission findings before public access.

Use fixture-based API/React regression tests plus real Google/browser checks on hosted Netlify and Render. Google's account consent and owner configuration are external prerequisites, so fixture success is not proof of hosted OAuth success. Keep changes isolated from Schedule C; apply only reviewed additive auth migrations with a private data snapshot and rollback plan. Feature-flag Google until configuration and end-to-end checks pass.

Revised planning estimate, not a measured guarantee: roughly one to two working days for the complete signup/linking/revocation/abuse-control/browser-QA scope. The earlier 4–8 hours understated that complete public-launch scope. Owner Google configuration may take about 30–60 minutes when domain/privacy prerequisites exist; external Google review, missing policy pages and separate tenant-isolation fixes are excluded. No paid auth-platform migration is necessary for this design; existing hosting/database capacity and any provider charges need separate confirmation if capacity changes. Implement the reviewed auth task independently, perform its QA cycle, and enable public signup only after the launch checks pass.
