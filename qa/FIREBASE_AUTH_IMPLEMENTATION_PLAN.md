# Firebase Authentication implementation plan

Status: research/design only. No Firebase project, accounts, credentials, dependencies, schema or hosted runtime changed. This replaces the standalone Google-signup direction: Firebase will manage email/password first, with Google available later through the same Firebase identity. Neon remains the business database. Schedule C stays isolated.

## Decisions and scope

- React uses the Firebase Web SDK; Render uses firebase-admin. Firebase holds authentication accounts/passwords and issues identity credentials. Render authorizes requests; Prisma/Neon retain existing User.id and all business foreign keys. Firestore and Firebase Hosting are not required.
- Use Firebase server session cookies, verified by Admin SDK, instead of retaining Firebase refresh tokens in browser storage or turning one verified ID token into an unchecked thirty-day Passport session. Start with a five-day cookie lifetime, within Firebase's supported five-minute/two-week range. Changes require actual session-risk/product review.
- Preserve the three approved existing users through authenticated migration. Public registration never picks an existing User.id, even if a username/email matches. Other registered legacy users remain unapproved until the owner explicitly authorizes their migration; do not auto-enable them.
- Public email/password signup requires a real email address, a compliant password and verified email before a Neon account/session with business access is created. The current @profittracker.invalid identifiers are not mailboxes and cannot receive verification/recovery messages. Do not carry the shared temporary password into Firebase.
- Google is a second method inside Firebase after email/password passes QA. Link Google to the same Firebase UID, never run a separate GoogleIdentity/GIS session implementation alongside Firebase. SMS login/MFA, account deletion and provider unlink are outside the first release; do not expose unfinished actions.

## Provider setup and security baseline

Use separate owner-controlled development and production Firebase projects. Enable email/password, configure password policy in Require mode (minimum 15 characters; accept long passphrases), enable email-enumeration protection, configure verified owned authorized domains and verification/reset templates and supported action URLs. Localhost authorization must be explicit for the development project. Do not disable enumeration protection to obtain convenient account-discovery APIs.

Pin supported SDK versions after checking Node/runtime compatibility. Render's Admin SDK uses a dedicated least-privilege server service account/appropriate supported credential mechanism. A private key belongs only in Render secrets/private local development configuration, never VITE variables, Git, screenshots or diagnostics. Firebase web configuration/API key is intentionally public; it is not an authorization boundary. Restrict keys appropriately to needed services and compatible clients, and never trust possession of a web key as proof of identity.

Confirm actual project plan, quotas, costs, email delivery limits and required production branding/privacy details before enabling public registration. No paid upgrade or account is created by this plan. MFA, Identity Platform and reCAPTCHA Enterprise/App Check integrations may introduce prerequisites/costs. Budget alerts are notification mechanisms, not guaranteed spending caps. Do not promise all Firebase features are included/free or that provider throttling eliminates every attack.

Layer Firebase protections with durable Render limits on exchange/signup/migration, trusted-proxy handling, bounded request sizes/concurrency/timeouts and exact Origin/CSRF validation. Client validation improves UX; Firebase/backend validation enforces rules. Rate-limit email resend/reset operations using Firebase's protections and any controlled app endpoints, with cooldown UI and generic messages. Attackers can call public Firebase endpoints directly; limits on our Render API alone cannot protect Firebase signup/email quotas.

Evaluate App Check for the custom API and separately for Firebase Auth/Identity Platform. These are different integrations with different prerequisites. Stage enforcement using metrics in development/staging, then test legitimate supported browsers before enabling it. Web attestation is an additional abuse signal, not a replacement for identity, authorization or request validation. Public release must document the selected provider-side abuse protections, costs and remaining limits; do not assume App Check is already enabled by adding an SDK.

Final research qualification: the reviewed Identity Platform App Check integration is currently documented as Pre-GA, with support/platform caveats. Do not make an untested Pre-GA feature the sole protection for public password endpoints. Confirm availability and supported operations in the actual project, plus pricing/terms, separately from the stable custom-backend attestation integration. Baseline password policy, enumeration protection, provider throttling, verified-email gating, controlled API limits and ownership checks remain mandatory. [Identity Platform documentation](https://docs.cloud.google.com/identity-platform/docs/admin/app-check-integration)

## Data models and contracts

Apply reviewed additive auth migrations only, from a branch based on hosted main. Inspect qa/QA_REPORT.md permission findings before implementation and public release. Preserve unrelated work and every business record. Save a provider restore point when available plus a private consistent data snapshot; verify before/after user IDs, record counts and fingerprints. Never run pending Schedule C/QA migrations during this cutover.

Proposed models:

| Model/field | Contract |
| --- | --- |
| FirebaseIdentity | Unique (project_id, firebase_uid), unique user_id FK to User.id; records verified identity metadata/migration status without passwords or tokens. One Firebase account per business user; password and Google can share it. |
| FirebaseSession | Unique SHA-256 fingerprint of issued cookie, FK to identity, expires_at/revoked status; raw Firebase cookie never stored. Enables logout of one session and rejecting replay of that cookie. |
| AuthIntent | Short-lived, one-use server-session-bound CSRF/login-or-migration intent; migration binds existing user ID, current credential version and recent reauthentication grant. Conditional consumption is atomic. |
| MigrationApproval | Owner-issued, expiring authorization for one existing User.id to one verified (project_id, Firebase UID). Never issued by public request data or inferred from email alone; consumed with the migration intent. |
| User.login_disabled | Account-wide server authority, checked fresh with identity/session state; an old five-minute User cache must not postpone revocation. |
| AuthAttemptBucket | Atomic durable counters/expiry for controlled API operations, with bounded cardinality and cleanup. Avoid an unbounded per-user account-lockout mechanism that attackers can use to deny legitimate access. |

Do not expose raw SDK errors, password hashes, service credentials, ID tokens, cookies or action codes in API responses/logs/Sentry. Return an explicit public user projection. Treat Firebase profile fields as untrusted display input; length-limit them and never accept roles, ownership IDs or permissions from profile/request data. Check both User.email and LocalCredential.email for legacy collisions. Store Firebase identity email separately; do not silently overwrite original Discord email or rename legacy local credentials.

## User flows and routes

### Public signup and existing Firebase login

1. React initializes Firebase once under StrictMode, sets inMemoryPersistence before authentication, and uses Firebase methods for signup/login. Passwords are sent to Firebase over HTTPS; the Render session endpoint receives only the ID token and intent proof. On successful server-cookie creation, sign out of the client SDK and clear token references. Do not persist tokens/passwords in localStorage or custom analytics.
2. For new signup, Firebase creates an auth account; send verification email. Show a verification-pending page without opening business screens. A refresh/restart can require sign-in again; do not store the password to avoid that. After email verification, reload the Firebase user and obtain a fresh ID token; require recent login when issuing the cookie.
3. POST /auth/firebase/intent establishes and explicitly saves an anonymous server session and creates a short-lived intent (initially five minutes). saveUninitialized is false in the current server, so reading req.sessionID alone is insufficient. Require the controlled custom header/allowed Origin, disable response caching and bind cookies/intent to the same browser session. Separate login/signup intent from migration intent; do not silently switch an authenticated account.
4. POST /auth/firebase/session verifies an ID token with verifyIdToken(token, true), the configured Firebase project/audience/issuer, verified email, enabled identity and recent auth_time (initially within five minutes). Verify the server's intent binding and CSRF proof; never accept a supplied audience/project allowlist. Firebase tokens are verified against the Firebase project, not a Google OAuth client ID or a raw Google sub.
5. Resolve an existing mapping to its User.id regardless of subsequent email changes. For new public signup, prepare creation after email/legacy-collision and signup-enabled checks; the actual User/identity writes occur in the transaction in step 6. Initialize only the new user's defaults. Unique constraints and explicit retry/conflict handling prevent duplicate/orphan users during simultaneous signup.
6. Create the Firebase session cookie outside the database transaction (no remote network work in transactions). Before issuing it, atomically consume the intent, create/confirm the identity/user and register the cookie fingerprint under current account status. If any database step fails, do not send the cookie. If the user/identity committed but the response was lost, retry must find the same account and issue a new session through a fresh intent. Do not delete a valid existing account as compensation for login failure. Recheck status/revocation as part of issuance and next authenticated request.
7. Send an HttpOnly, Secure, Path=/, host-only cookie (prefer a dedicated __Host-pt_firebase_session name). The chosen five-day expiry must match cookie attributes and FirebaseSession expiry. Keep the existing configured API origin as the initial canonical production transport; the frontend and API are HTTPS subdomains of the same site, so start with SameSite=Lax and verify the complete chosen flow. Do not mix cookies belonging to the frontend and API host within a session. Test direct-origin and proxy cases independently, including CORS/preflight and forwarded HTTPS headers. Do not widen Domain to share cookies unnecessarily; the proxy must not become an accidental second login transport.

Auth request limits must run before the current seven-megabyte global JSON parser. Only narrow login/intent recovery routes can disregard an invalid legacy session. Migration/account-management routes retain full authentication. A broad /auth/firebase/* guard bypass is forbidden.

### Authenticated requests, logout and recovery

Shared authentication middleware verifies the dedicated Firebase cookie using verifySessionCookie(cookie, true), then checks fresh identity mapping, account-disabled status and active unexpired cookie fingerprint before attaching the existing User.id to req.user. Token verification with no revocation check is insufficient. Validate role/ownership on every related ID in the existing routers; Firebase Security Rules do not protect Neon or Express automatically.

Start with revocation checks on each authenticated request; bound network calls, coalesce identical concurrent verification work within one request wave where safe, and fail closed on provider verification outages. Measure actual latency/quotas before considering any documented revocation-cache window. Do not silently accept stale revocation state to keep the site appearing available.

POST /auth/logout revokes the current cookie fingerprint and clears cookies using matching Path/host attributes. Old cookie replay must fail. Logout-all/owner disable revokes all local FirebaseSession rows, disables locally where appropriate and calls Firebase revokeRefreshTokens; local denial happens first so a provider failure cannot leave business access open. Retrying remote revocation is idempotent. Ordinary logout does not revoke Google's entire consent grant.

Forgot-password and verify-email use Firebase supported action flows with generic enumeration-safe UI, resend cooldowns, approved action origins and no open redirects. Password reset is not proof of existing Neon ownership; it affects the same already-mapped Firebase UID. After reset/major changes, enforce provider revocation and fresh login; test old session and new-password behavior. Sensitive operations require recent Firebase reauthentication before minting a fresh app session or changing mappings. With in-memory frontend persistence, a user must authenticate again to manage Firebase account settings.

Firebase automatically revokes existing tokens on password reset; revocation-aware server-cookie verification must actually enforce that behavior. Settings password changes use Firebase reauthentication/updatePassword for the exact already-mapped UID, not the retired Render change-password endpoint. Verification/reset action codes must stay out of telemetry, referrers and arbitrary continue URLs; use the current web action flow and reviewed SDK, not deprecated Dynamic Links assumptions. Email-send limits and Admin-generated-link quotas are different: the reviewed Spark table lists 150 reset emails/day versus 1,500 generated reset links/day; recheck the actual project at release and alert on delivery/quota failures. [Revocation](https://firebase.google.com/docs/auth/admin/manage-sessions), [Limits](https://firebase.google.com/docs/auth/limits), [Email action state](https://firebase.google.com/docs/auth/web/passing-state-in-email-actions)

On logout/login/account switch, clear or namespace TanStack Query caches by current User.id and discard stale auth callbacks. Business API authentication failures should clear/expire app auth state and show a login/retry path, not continue rendering another user's cached data. Provider failures return safe 503/retry states; invalid/revoked sessions return 401; unverified email never gets business authorization.

### Migration of the three approved users

1. Owner privately verifies which existing account each real email belongs to; do not commit a private mapping roster. Users first complete the current temporary-password change. A shared temp password alone is not sufficient migration proof; require a recent private-password reauthentication grant bound to the current account/version plus a server-side MigrationApproval for the exact target Firebase UID. After the user has created/verified their Firebase identity, an owner-only trusted CLI checks that provider user and records the expiring approval. Public endpoints cannot issue this approval.
2. While signed into that existing account, enter migration mode before creating/signing into Firebase. Authenticate the target Firebase identity using a real email/private password and verify its email. Firebase signup creates only a provider account at this point; do not automatically create a new Neon account from that migration flow. If an email already exists in Firebase, sign into/recover that Firebase account instead of creating a duplicate.
3. POST /auth/firebase/link verifies both current local account access/reauthentication and a recent verified Firebase token, plus the migration intent and owner-approved target UID. In one Neon transaction, attach the Firebase identity to the authenticated legacy User.id, consume both grants, verify uniqueness/status, register the new Firebase cookie fingerprint and retire that user's local credential (disabled plus version increment). Create the cookie through Firebase before this transaction but do not issue it until the commit succeeds. Existing User.email, UUID and business data remain unchanged. A UID already attached elsewhere is rejected without moving any records. If an account has already created a separate Neon user, stop and record a separate owner-reviewed reconciliation task; no automatic data merge.
4. Establish/register the Firebase cookie as part of the successful transition; invalidate that account's legacy sessions. If the network/session response fails after mapping commit, Firebase login recovers the same account. Do not report that migration never happened or reopen retired local credentials automatically. Keep migration auditable through safe account IDs/status/timestamps only.
5. Migrate/test the owner first, then the other two. Verify per-user inventory/sales/settings counts and actual browser access, logout/new login and session persistence across a Render restart. After all three succeed, remove the legacy password entry/forced-change code from the public UI and retire Passport authentication in a separate focused cleanup. During rollout, migrated users cannot bypass Firebase resets/revocation by using old local login.

Global rollback is not just deploying the old password-only guard: Google/Firebase-only users would be locked out and migrated local credentials are retired. Use staged feature flags to stop NEW registration independently of returning Firebase login; keep the compatible session verifier available. Restore a legacy login only through an explicit owner-controlled recovery/reset of the same account after identity proof. Additive auth data should not be dropped during runtime rollback.

During mixed-cookie rollout, use deterministic provider selection. An invalid Firebase cookie must never silently fall back to an old local credential/session. Conflicting authenticated identities are rejected except in the narrowly authorized migration route, where both identities must match its server-side approval. Account-wide disablement also applies to legacy login/guard routes. Cleanup of unused provider accounts is reviewed separately; failed signup does not authorize automatic Firebase account deletion.

### Optional Google phase

Use Firebase GoogleAuthProvider with signInWithPopup on a direct user gesture for desktop. Verify/link through Firebase's account-linking APIs while signed into the intended Firebase user; business ownership remains the same mapped Firebase UID. Google authorization credentials are configured under that provider, not sent to Render as independent Google tokens. Handle provider/email conflicts through proof of both accounts, with no email-only merge and no unsolicited permissions beyond identity.

For redirect mode/mobile fallback, follow Firebase's current third-party-storage guidance for a non-Firebase-hosted site; simply setting authDomain to our Netlify hostname is insufficient. Configure/test any required auth helper proxy/approved domains first. Normal supported browsers are the acceptance environment; embedded webviews can be rejected. No bypass of Google security restrictions. Check the documented known provider-linking issue against pinned SDK versions and exercise the exact chosen linking flow before enabling it.

## Implementation order and QA acceptance

Work on one focused task at a time. For each: implement -> normal/failure/security QA -> fix -> repeat QA; do not proceed past known errors in that scope. Record unrelated issues separately. Overall QA follows after the combined feature is complete.

| Stage | Work | Must pass before next stage |
| --- | --- | --- |
| 0 | Config/secret/price review, existing owner access and permission findings | Correct project/domain and private real-email mapping; public access stays disabled; any unresolved cross-tenant finding blocks public release. |
| 1 | Additive identity/session/intent/limit models and shared verifier | Request/ownership validation, exact-project checks, atomic consumption, rollback, expired/revoked/disabled denial and no raw credentials in logs. |
| 2 | Email signup/login/verification/reset UI and cookie exchange | Normal and empty/invalid input; email resend/reset; token refresh after verification; cancel/retry; duplicate submits; safe post-commit recovery; account-switch cache isolation. |
| 3 | Owner then two user migrations | Both-account proof; stale/expired/replayed grants denied; concurrent linkage conflict; same UUID/data/permissions; retired password denied; provider outage recovery. |
| 4 | Public controls plus combined hosted QA | Real unrelated signup, limits across restart/replicas, legitimate shared-IP behavior, single/all logout replay denial, reset revocation, actual restart persistence, supported desktop/mobile/PWA browsers. |
| 5 | Optional Google through Firebase | Same Firebase UID when linked; cancellation/provider conflict; popup/redirect storage compatibility; returning login unaffected by signup-disabled flag. |

Regression matrix must cover: forged/unsigned/wrong-project/expired tokens; revoked/disabled provider or local accounts; absent/wrong CSRF/origin/header/cookie; omitted optional fields and unexpected IDs/roles; email collisions in both email stores; simultaneous first signup/replay/linkage; failures before and after database commit; Firebase account exists with no Neon mapping; mapping exists but cookie registration/response failed; per-session/all-session logout; password reset/email change; cache leakage/account switching; quota exhaustion/outage; old legacy session after migration; expired/unverified email actions; legitimate users sharing a network.

Use Firebase Auth Emulator plus isolated PostgreSQL/fixtures, backend integration and React tests, lint/build/Prisma validation, then real staging Firebase and hosted API/browser checks. Production must fail startup if FIREBASE_AUTH_EMULATOR_HOST is present: the emulator deliberately accepts unsigned credentials. Emulator success cannot verify real email delivery, Google consent, throttling/App Check, billing or production signatures. External gaps stay explicitly pending.
