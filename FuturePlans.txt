2. CORE WORKFLOW & STATUS AUTOMATION
================================================================================

--------------------------------------------------------------------------------
2.1 Lean Status Architecture
--------------------------------------------------------------------------------
Separates inventory receiving status from sales fulfillment status. Do not store every condition as a separate monolithic enum.

[A] Inventory Receiving Pipeline:
    PRE_ORDER -> PURCHASED -> INBOUND -> ON_HAND
- `PRE_ORDER`: Vendor has not yet released or shipped the purchase.
- `PURCHASED`: Order placed; no active tracking yet.
- `INBOUND`: Inbound carrier tracking number attached; package in transit.
- `ON_HAND`: Item received and physically held. Terminal receiving state.
- Derived Availability:
  * `qty_on_hand > 0` -> Available
  * `qty_on_hand == 0` -> SOLD_OUT (calculated dynamically, not a stored receiving status)
  * Listing status is an orthogonal boolean/state: `UNLISTED` vs. `LISTED`.

[B] Sale Workflow Pipeline:
    AWAITING_SHIPMENT -> OUTBOUND -> [Workflow Steps] -> WAITING_FOR_PAYMENT -> PAID
- `AWAITING_SHIPMENT`: Shown as "Sold — Waiting to Ship".
- `OUTBOUND`: Replaces legacy `SHIPPED_OUT`. Tracking attached.
- `WAITING_FOR_PAYMENT`: Outbound delivery confirmed; waiting for platform payout.
- `PAID`: Final successful state. Payout received and reconciled.
- Exception states (outside normal progression):
  `CANCELLED`, `RETURN_IN_PROGRESS`, `RETURNED`, `DISPUTED`, `AUTHENTICATION_FAILED`.

Multi-Unit Integrity:
- Purchase of 5 units: receiving status stays `ON_HAND`.
- Selling 2 units decreases `qty_on_hand` from 5 to 3 and creates a Sale row with status `AWAITING_SHIPMENT`.
- UI display: "3 available · 2 outbound".

--------------------------------------------------------------------------------
2.2 Platform-Specific Workflows
--------------------------------------------------------------------------------
When a sale is created, it inherits a workflow based on platform settings:

1. Standard Marketplace (eBay, Mercari):
   AWAITING_SHIPMENT -> OUTBOUND -> Carrier Delivered -> WAITING_FOR_PAYMENT -> PAID

2. Authentication Marketplace (StockX, GOAT):
   AWAITING_SHIPMENT -> OUTBOUND -> DELIVERED_TO_AUTHENTICATOR -> AUTHENTICATING -> WAITING_FOR_PAYMENT -> PAID
   * Exception: AUTHENTICATING -> AUTHENTICATION_FAILED -> RETURN_IN_PROGRESS -> RETURNED.
   * Note: Do not restore inventory when authentication fails; only restore after physical item is returned and accepted.

3. Cash-Out / Buyback Provider (ElectronicsBuyer, Buying Groups):
   AWAITING_SHIPMENT -> OUTBOUND -> DELIVERED_TO_PROVIDER -> WAITING_FOR_SCAN_IN -> SCANNED_IN -> [ACCEPTED] -> WAITING_FOR_PAYMENT -> PAID

4. Direct or Local Sale (In-person, Cash):
   AWAITING_HANDOFF -> HANDED_OVER -> WAITING_FOR_PAYMENT -> PAID (or direct to PAID if paid on handoff).

--------------------------------------------------------------------------------
2.3 Tracking Event Milestones & Automations
--------------------------------------------------------------------------------
- Milestone Timestamps: `received_at`, `delivered_at`, `paid_at`, `cancelled_at`.
- Routine Tracking Updates:
  * Inbound tracking added -> moves `PURCHASED` to `INBOUND`.
  * Carrier reports inbound delivered -> records `delivered_at`, `received_at`, advances to `ON_HAND`.
  * Outbound tracking added -> moves `AWAITING_SHIPMENT` to `OUTBOUND`.
  * Carrier reports outbound delivered -> records `delivered_at`, advances sale to next workflow step (e.g. `WAITING_FOR_PAYMENT` or `AUTHENTICATING`).
- Optimization: Shared tracking numbers across multiple items trigger only one carrier API lookup and batch update all related items.

--------------------------------------------------------------------------------
2.4 User Action Registry, Confirmation & Undo Policies
--------------------------------------------------------------------------------
Contextual Action Buttons (Replace unrestricted dropdowns):
- Pre-Order: [Mark Purchased], [Cancel]
- Purchased: [Add Tracking], [Mark On Hand]
- Inbound: [Check Tracking], [Mark On Hand]
- On Hand: [List Item], [Record Sale]
- Listed: [Record Sale], [Unlist]
- Sold — Waiting to Ship: [Add Outbound Tracking]
- Outbound: [Check Tracking]
- Authenticating: [Mark Passed], [Mark Failed]
- Waiting for Scan-In: [Mark Scanned In]
- Waiting for Payment: [Mark Paid]
- Paid: Completed (Read-only)

Confirmation Policy:
- Routine Actions (No dialog, show temporary toast with "Undo"):
  Add tracking, mark on hand, list/unlist, mark scanned in, submit sale form, mark paid.
- Destructive Actions (Explicit confirmation modal required):
  Void sale, cancel after shipment, reopen paid sale, report dispute, mark authentication failed, manual inventory quantity overrides.
- Void vs Cancel vs Return:
  * Void: Sale was entered in error. Restores inventory, completely excludes sale from P&L.
  * Cancel: Valid sale was cancelled. Preserves historical record, restores inventory.
  * Return: Preserves sale and payment; inventory is restored only after item return is inspected and accepted.

--------------------------------------------------------------------------------
2.5 Legacy Status Migration Mapping
--------------------------------------------------------------------------------
Normalize stored database values to uppercase canonical constants:
- `Pre Order` -> `PRE_ORDER`
- `PURCHASED` -> `PURCHASED`
- `SHIPPED_IN` -> `INBOUND`
- Inbound `DELIVERED` or `SCANNED_IN` -> `ON_HAND`
- `LISTED` -> `is_listed = true` + `ON_HAND`
- `SOLD` -> `AWAITING_SHIPMENT`
- `SHIPPED_OUT` -> `OUTBOUND`
- `AUTHENTICATION` -> `AUTHENTICATING`
- `COMPLETED` -> `PAID` (where payout was confirmed)

3. TAXES & COMPLIANCE
================================================================================

--------------------------------------------------------------------------------
3.1 Full Schedule C Worksheet (Parts I–V & Form 8829)
--------------------------------------------------------------------------------
Goal: Expand current partial Part II implementation into a full Part I–V worksheet.

- Part I: Gross Income
  * Gross receipts = sum of realized sales (`unit_price * quantity`).
  * Returns and allowances = customer refunds and return adjustments.
  * Other income = manual entries (promotions, settlements, shipping insurance payouts).
- Part II: Expenses (Expanded ~24 Category Taxonomy)
  * Line 9: Car and truck expenses
  * Line 11: Contract labor
  * Line 13: Depreciation and section 179
  * Line 14: Employee benefit programs
  * Line 15: Insurance (other than health)
  * Line 16a/b: Mortgage interest / Other business interest
  * Line 18: Office expense
  * Line 19: Pension and profit-sharing plans
  * Line 20a/b: Rent/lease (vehicles/equipment vs. other business property)
  * Line 21: Repairs and maintenance
  * Line 22: Supplies
  * Line 23: Taxes and licenses
  * Line 24a/b: Travel / Deductible meals (with 50% IRS limitation calculation)
  * Line 25: Utilities
  * Line 26: Wages
  * Line 27a: Other expenses (itemized from Part V)
- Part III: Cost of Goods Sold (COGS)
  * Line 33: Inventory method selection (Default: Cost / Specific Identification).
  * Line 35: Beginning inventory (manual entry / prior year ending inventory).
  * Line 36: Purchases less personal withdrawals = derived from `batchCost(inventory)` for tax year.
  * Line 37: Cost of labor.
  * Line 38: Materials and supplies.
  * Line 39: Other costs (inbound freight/shipping).
  * Line 41: Ending inventory (manual entry / physical inventory valuation).
- Part IV: Information on Your Vehicle
  * Feeds into Line 9. Records placed-in-service date, business vs commuting vs personal mileage, evidence availability.
- Part V: Other Expenses Detail
  * Itemized breakdown of software subscriptions, platform listing fees, bank/merchant processing fees, packaging supplies.
- Form 8829: Expenses for Business Use of Your Home
  * Simplified method ($5/sq ft up to 300 sq ft = max $1,500) vs. actual expenses. Feeds Schedule C Line 30.

New Tables Required:
- `ScheduleCYearDetail` (`user_id`, `year`, `other_income_decimal`, `inventory_method`, `beginning_inventory_decimal`, `cost_of_labor_decimal`, `materials_supplies_decimal`, `other_costs_decimal`, `ending_inventory_override_decimal`).
- `ScheduleCVehicle` (`user_id`, `year`, `description`, `placed_in_service_date`, `business_miles`, `commuting_miles`, `total_miles`, `method`, `actual_expenses_decimal`).
- `ScheduleCHomeOffice` (`user_id`, `year`, `method`, `business_sqft`, `home_sqft`, `actual_expenses_decimal`).

--------------------------------------------------------------------------------
3.2 Business Tax Profile & Income Accounting
--------------------------------------------------------------------------------
Profile Data Model (Per user/business entity and tax year):
- Entity type (Sole Proprietorship, Single-Member LLC).
- Business name / DBA, EIN, Business address.
- Principal business description and 6-digit NAICS code.
- Accounting method: Cash vs. Accrual.
- 1099 question: Were payments made requiring 1099 filing? Were they filed?

Reseller Income Structure:
  Gross Receipts (Customer charges + shipping charged)
  - Returns and Allowances
  = Net Receipts
  - Cost of Goods Sold (COGS)
  = Gross Profit
  - Platform Fees & Outbound Shipping
  - Operating Overhead & Other Business Expenses
  = Net Profit

--------------------------------------------------------------------------------
3.3 Inventory Valuation & COGS
--------------------------------------------------------------------------------
- Specific Identification Method at actual purchase cost (purchase price + nonrefundable sales tax + inbound shipping).
- Purchase Adjustments: Vendor credits, partial refunds, coupon corrections, and sales tax refunds link to the original purchase batch and reduce unit cost basis.
- Personal Withdrawals: Flag items removed from inventory for personal use to exclude from COGS.

--------------------------------------------------------------------------------
3.4 Vehicle & Mileage Tracking
--------------------------------------------------------------------------------
- Recommended initial implementation: Stride CSV import parser with duplicate detection and manual review queue.
- Trip attributes: Date, miles, origin/destination, business purpose, related purchase/shipment ID, deduction method (standard IRS mileage rate vs. actual expenses). Parking and tolls tracked separately as 100% deductible travel/transportation expenses.

--------------------------------------------------------------------------------
3.5 Equipment & Depreciation Asset Register
--------------------------------------------------------------------------------
- Differentiate:
  * Inventory: Goods bought for resale.
  * Supplies: Consumables (boxes, poly mailers, bubble wrap, thermal labels).
  * Equipment/Assets: Long-term operational tools (computers, label printers, cameras, shelving, dollies).
- Asset Fields: Name, serial number, vendor, receipt link, purchase date, placed-in-service date, cost basis, business-use %, proposed tax treatment (Section 179 expense vs. MACRS depreciation).

--------------------------------------------------------------------------------
3.6 Home Office Deduction
--------------------------------------------------------------------------------
- Reseller-specific rules: Support both dedicated exclusive office workspace and dedicated inventory storage areas (qualifies even if shared space if home is the only fixed business location).
- Fields: Total home sq ft, business sq ft, storage sq ft, months active, method (simplified vs. actual expenses: rent, mortgage interest, property taxes, utilities, insurance, maintenance).

--------------------------------------------------------------------------------
3.7 Reseller Tax-Exempt & Resale Certificate System
--------------------------------------------------------------------------------
Separate into 3 distinct tax mechanisms:
1. Reseller buying inventory tax-free for resale:
   - Resale certificate profile: Purchaser name, address, state jurisdiction, resale certificate permit number, document PDF upload, expiration date.
   - Per purchase: Flagged tax-exempt, certificate attached, vendor sales tax charged/refunded.
2. Reseller selling tax-free to other businesses/cash-outs:
   - Buyer resale certificate verification, permit number, destination jurisdiction.
3. Marketplace Facilitator Collection:
   - Clear identification when eBay/StockX collects and remits customer sales tax.
   - Replaces vague `customer_tax_exempt` boolean with explicit tax collector assignment.

================================================================================

--------------------------------------------------------------------------------
4.1 Buying-Group Live Deals Feed (parsefile Platform Integration)
--------------------------------------------------------------------------------
Source & Architecture:
- Supported groups: Points4Days, MVP Buying Group, MaxOut Deals, Big Deal Points, BuyersForPoints.
- Unified Architecture: All 5 groups run on the identical `parsefile` web platform; one client implementation handles all five by swapping the base URL.
- Authentication & Payload Encryption:
  * `SESSID` cookie bootstrap and encrypted POST login requests.
  * Encrypted payloads: AES-256-CBC, OpenSSL `EVP_BytesToKey` key derivation using MD5 and `SESSID` as password, 8-byte salt.
  * Format: `{ "_encrypted": JSON.stringify({ ct, iv, s }) }`.
- Deals Feed Reading:
  * Reads `it@deals` / `it@deals-card` table data.
  * Fields mapped: Deal ID (`t_f_id`), Title (`t_f_title`), Group payout price (`t_f_total`), Retail price (`t_f_retail`), Insurance coverage (`t_f_insurance`), Availability (`t_f_enabled && t_f_active && !t_f_full`), Order commitment requirement (`t_f_order_required`).
- Integration into Cashouts Page:
  * Plugs into existing `services/cashouts/` architecture (`registry.js`, `dealPresenter.js`).
  * Encrypted credential storage in `CashoutConnection`.
  * Bot/Captcha Guard: If Cloudflare Turnstile or 2FA challenge is detected, fail safely and alert user to reconnect.

--------------------------------------------------------------------------------
4.2 Automatic Tracking Sync & Delivery Calendar
--------------------------------------------------------------------------------
- Scheduled Background Sync:
  * Background cron job running every 2–4 hours using PostgreSQL advisory locks.
  * Syncs active in-transit shipments (oldest refreshed first, skips delivered/returned packages).
- Expanded Carrier Coverage:
  * DHL: Official DHL Unified Tracking API integration (`services/carriers/dhl.js`).
  * Amazon (`TBA...`): Direct carrier tracking links (`https://track.amazon.com/tracking/<num>`).
- Auto-Upload Tracking to Buying Groups:
  * BuyingGroup.com API (`POST /v1/order/add_trackings`).
  * `parsefile` groups: Upload tracking numbers via `uploadTrackings` on `it@orders`.
- Shipping Delivery Calendar:
  * Top of `Shipping.jsx` page: Summary stats (Arriving Today, This Week, No ETA, Not Moving, Delivered).
  * Day strip: Cards per day showing incoming package count and total purchase value.
  * Filter tabs: "Not Moving" tab for packages created but not yet in carrier transit after N days.

--------------------------------------------------------------------------------
4.3 Additional Reseller Tool Ideas
--------------------------------------------------------------------------------
- Email Order Import: IMAP/Gmail integration to parse retailer purchase confirmations and shipping notices automatically.
- Best Payout Across Groups & Historical Trends: Compare live payouts between ElectronicsBuyer, Points4Days, MVP, etc., and display price trend charts.
- Deal & Delivery Webhook Alerts: Discord webhook pings when target deals appear or shipments arrive.
- Gift Card Tracker: Track individual gift card balances, cards used on purchases, and remaining balances.
- Price-Drop / Price-Match Tracker: Monitor purchases inside retailer price-adjustment windows to claim refunds.
- Amazon Order History CSV Import: Bulk purchase creation from downloaded Amazon B2B/consumer order history.

--------------------------------------------------------------------------------
5.1 Invoices & Accounts Receivable
--------------------------------------------------------------------------------
Purpose: Manage B2B / wholesale sales and bulk cash-out payouts where funds are owed but not yet received.
- Data Schema:
  * `invoices`: `id`, `user_id`, `buyer_id`, `amount_due`, `amount_paid`, `status` (`DRAFT`, `SENT`, `PARTIAL`, `PAID`, `OVERDUE`), `due_date`, `created_at`.
  * `invoice_sales` (Pivot): `invoice_id`, `sale_id`.
- Cash Flow Integration: Outstanding balance (`amount_due - amount_paid`) directly calculates into "Total Owed" on the Cash Flow dashboard.

--------------------------------------------------------------------------------
5.2 Receipts Management & Cloud Storage
--------------------------------------------------------------------------------
- Orphaned Receipts Inbox ("Action Needed"):
  * Allow users to upload receipts (images/PDFs) before entering transactions.
  * Receipts with `linked_record_id = null` stay in an unassigned inbox until attached to an inventory purchase or expense.

--------------------------------------------------------------------------------
5.3 Forecast Planner, Simulation Engine & Goal Tracking
--------------------------------------------------------------------------------
- Baseline Analytics (Past 90 days):
  * Average Yield: Marketplace ROI vs. Churning cashback yield.

- Goals Model:
  * Table `goals`: `id`, `user_id`, `goal_type` (`WEEKLY_PROFIT`, `MONTHLY_VOLUME`, `UNITS_SOLD`), `target_amount`, `start_date`, `end_date`.
  * Dashboard visual progress rings comparing live realized metrics against target amounts.
